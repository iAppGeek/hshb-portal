# Portal refactor — programme overview

This folder is a set of **independent, incrementally deliverable plans** that together raise the
portal's code quality, consistency and mobile experience. Each numbered file is a self-contained
brief for a coding agent: it fixes the architecture and library choices up front so the agent only
has to implement, not decide.

`00-analysis.md` is the full audit that these plans came from. Read it for the evidence; read this
file for the rules; read one numbered plan to do the work.

## Aim

1. **Easy to read and maintain.** One way to do each thing: one form system, one action pattern, one
   auth helper, one route config, two grids, one schema source.
2. **Reuse over per-screen variants.** Shared components and helpers replace the 27 copies of
   `Field`, the 72 hand-rolled `auth()` checks, the four tab bars, the duplicated Add/Edit forms.
3. **Logic in the right layer.** Behaviour in TypeScript; data shape and integrity constraints in the
   database schema; nothing in PL/pgSQL. Aggregation happens in one typed query, not in JS `Map`s.
4. **Fast on a teacher's phone.** Fewer round-trips per interaction, no page re-fetch after a save,
   skeletons while data streams, less client JavaScript on teacher screens.

## Product constraints (non-negotiable)

- Teachers use the portal on mobile, often on poor signal. Perceived speed of page load and save
  feedback comes before anything else on teacher-facing screens.
- Minimise SQL. The team does not have SQL depth; application-layer TypeScript is preferred.
- Photo opt-out stays. Push notifications stay.
- No behaviour change unless the plan says so. Refactors must be invisible to users except where a
  plan lists a deliberate UX change.

## Decisions already made — do not reopen inside a plan

| Area                | Decision                                                                                                                                                                                                                                                                                  |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Framework           | Next.js 16 App Router, React 19, React Compiler on. Server components by default; `'use client'` only for interaction.                                                                                                                                                                    |
| Database access     | **Drizzle ORM** with the `postgres` (postgres.js) driver over a direct Postgres connection (`DATABASE_URL`, Supabase Supavisor transaction pooler in production, port 6543). `supabase-js` is removed once plans 09 and 10 are done. No Supabase Auth, RLS policies, Storage or Realtime. |
| Schema source       | `src/db/schema.ts` (Drizzle). Migrations generated by `drizzle-kit generate` into `supabase/migrations/` with the `supabase` timestamp prefix; applied by the Supabase CLI exactly as today. `supabase/schema.sql` and `src/types/database.ts` are deleted at the end of plan 10.         |
| Transactions        | `db.transaction(async (tx) => …)` in TypeScript. Every former PL/pgSQL function becomes a TS function in `src/db/*.ts`. Tables keep their FKs, `CHECK`s and unique indexes.                                                                                                               |
| Caching             | **None** at the query level. No `unstable_cache`, `updateTag`, `revalidatePath`, `revalidateTag`. Pages are dynamic and read fresh data. (Revisit only after the region check in "Owner tasks" below, and then only with `'use cache'` at segment level.)                                 |
| Auth                | NextAuth v5 + Entra ID unchanged. `requireSession()` / `requireRole()` in `src/auth/require.ts` are the only way pages get the actor. `runAction()` in `src/lib/action.ts` is the only way server actions are written.                                                                    |
| Validation          | Zod 4 in the action layer via `runAction({ schema })`. Field-level errors via `z.flattenError`. HTML `required` as first-line defence. No validation logic in SQL beyond constraints.                                                                                                     |
| Forms               | `src/components/form/*` kit + `useServerForm` hook. One form component per entity used by both `new` and `[id]/edit` routes. No `useActionState`; no react-hook-form or other form library.                                                                                               |
| Tables              | Exactly two: `SimpleGrid` (server, zero JS) and `FunctionalGrid` (client, TanStack). Teacher-facing lists use `SimpleGrid` unless search is required. No hand-rolled `<table>`s.                                                                                                          |
| Entity navigation   | Every entity follows list → view (`/x/[id]`) → edit (`/x/[id]/edit`). No detail modals.                                                                                                                                                                                                   |
| Routing/permissions | `src/lib/routes.ts` is the single list of routes, labels, icons and permissions; `proxy.ts`, the sidebar and `requireRole` all read from it.                                                                                                                                              |
| Styling             | Tailwind 4 + existing tokens in `src/lib/grid/styles.ts`. Headless UI stays for dialogs/menus. Heroicons stays.                                                                                                                                                                           |
| Logging             | `logError(scope, err, context?)` in `src/lib/log.ts` wrapping `console.error`. No logging vendor in this programme.                                                                                                                                                                       |
| Tests               | Vitest unit tests for pure logic and components; `*.int.spec.ts` integration tests for `src/db` against the local Postgres (run in the E2E CI job); Playwright for flows. Tests assert outcomes, not which internal function was called.                                                  |
| Dependency versions | Pin exact versions in `package.json` (repo convention). Do not add dependencies a plan doesn't name.                                                                                                                                                                                      |

## Owner tasks (not for coding agents)

- **Region check.** Confirm the Supabase project region and set the Netlify functions region to
  match (EU). Do this before plan 03 lands so the "no cache" decision is measured fairly.
- **Product decisions.** Plan 13 (class roll-over) changes a workflow; approve or drop it.
- **Production migrations.** Continue applying `supabase/migrations` to production with
  `supabase db push` after each plan that adds a migration (09, 10, 01).

## Conventions every plan follows

- One branch per plan: `refactor/NN-short-name`. Conventional commits (`refactor(scope): …`), as
  enforced by commitlint.
- `npm run pipeline:check` must pass before the PR is opened (lint, format, type-check, coverage
  thresholds, E2E, build). Coverage thresholds in `vitest.config.ts` must not be lowered.
- Delete replaced code in the same PR. No `// TODO remove` shims left behind unless the plan
  explicitly stages it.
- When a plan says "all call sites", find them with `rg` and list them in the PR description.
- Update `README.md` / `src/lib/PERMISSIONS.md` / `.env.local.example` when a plan changes what they
  describe.
- Do not change user-visible copy, colours or layout unless the plan lists it under "Deliberate UX
  changes".
- If something in the codebase contradicts the plan (a file moved, a signature changed), follow the
  plan's intent, note the discrepancy in the PR, and do not redesign.

Each phase leaves `main` shippable. Plans inside a phase are independent of each other and can run
in parallel on separate branches.

| 3     | 05, 08, 11     | Merge forms, lists/entity pages, review flows. Consume the kits from phase 2.                    |

| 6     | 13             | Optional.                                                                                        |

## Definition of done for the programme

- `rg "await auth\(\)" src --glob '!*.spec.*'` returns only `src/auth/require.ts` and `src/app/layout.tsx`.
- `rg "function Field\(|function TextField\(|function Section\(" src/app` returns nothing.
- `rg "unstable_cache|updateTag|revalidatePath|revalidateTag" src` returns nothing.
- `rg "\.rpc\(|@supabase/supabase-js" src e2e` returns nothing; `supabase/schema.sql` and
  `src/types/database.ts` are gone; `supabase/migrations` contains no `CREATE FUNCTION`.
- Every `src/app/**/page.tsx` that renders a heading uses `PageHeader`; every `[id]` route calls
  `notFound()` on a missing record; `src/app/not-found.tsx` and `src/app/error.tsx` exist.
- Every list renders through `SimpleGrid` or `FunctionalGrid`.
- `npm run pipeline:check` is green and coverage thresholds are unchanged or higher.
